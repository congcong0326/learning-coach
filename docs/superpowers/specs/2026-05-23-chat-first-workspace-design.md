# 做题工作台 Chat-first 交互设计

## 1. 背景

当前做题工作台已经具备训练会话、教练消息、代码快照、LeetCode 回填和复盘 run 的工程基础，但页面形态偏向三栏卡片：

```text
题面卡片 | 代码卡片 | 教练卡片
```

这个形态和产品主线存在偏差。产品第一版不做站内代码运行、不自建判题，用户真正写代码、运行和提交仍以 LeetCode 官网为准。工作台的核心价值应是 AI 教练对话、代码 review、提交后复盘和画像沉淀，而不是在站内提供一个轻量 IDE。

本设计把工作台收敛为：

```text
左侧题面 | 右侧 ChatGPT 式 AI 教练
```

代码记录、提交状态和复盘入口仍保留，但改为围绕聊天流和结构化训练事实展开。

## 2. 设计目标

- 降低用户进入做题后的界面负担，让主要操作集中在教练聊天中。
- 保留代码快照和提交事实，支撑后续错因归因、复盘和画像更新。
- 避免让用户误以为产品已经接入 LeetCode 自动提交或站内判题。
- 让“代码 review -> AI 判断 -> LeetCode AC -> 复盘”的闭环更自然。

## 3. 非目标

- 不做站内代码编辑器或本地运行入口。
- 不自动提交 LeetCode。
- 不抓取 LeetCode 提交历史、隐藏用例、运行时间或内存消耗。
- 不把红灯/绿灯定义为真实判题结果。
- 不扫描全部聊天内容来猜测代码记录，避免误提取普通文字或伪代码。

## 4. 页面结构

工作台使用两栏布局：

```text
┌───────────────┬──────────────────────────────┐
│ 题面           │ 教练聊天                      │
│               │ 顶部状态区                    │
│ 中文题面       │ - 阶段                         │
│ LeetCode 链接  │ - 提示档位                     │
│               │ - 训练模式                     │
│               │ - 代码尝试记录按钮              │
│               │                              │
│               │ 聊天时间线                    │
│               │ 输入区 / 请求提示 / 已 AC       │
└───────────────┴──────────────────────────────┘
```

右侧不再把画像快照、事件时间线和代码草稿作为主要卡片展示。画像和事件仍然作为后端上下文与调试信息存在，用户界面只展示对当前训练决策有帮助的轻量状态。

## 5. 教练聊天区

聊天区展示以下内容：

- 用户自然语言消息。
- 用户粘贴的代码块。
- AI 教练回复。
- 代码 review 结果。
- 结构化业务事件，例如“已记录一次代码尝试”“用户标记 LeetCode AC”“复盘已生成”。
- 复盘摘要卡片。

输入区保留自然语言输入，并提供少量明确动作：

- 发送。
- 请求提示。
- LeetCode 已 AC。

“请求提示”是结构化动作，用于提升或触发提示策略。“LeetCode 已 AC”是用户声明的最终训练事实，用于结束本题并触发复盘。

## 6. 代码尝试记录

### 6.1 命名

用户可见入口命名为“代码尝试记录”，不使用“代码提交记录”。

原因是这些记录可能来自聊天中的代码 review，并不一定真的提交到了 LeetCode。使用“提交记录”容易暗示系统接入了 LeetCode 官方提交历史。

### 6.2 生成规则

代码尝试记录自动生成，但必须满足训练状态约束：

```text
只有当教练流程进入 review_code 阶段时，
才从本轮用户消息中提取明确代码，
并生成代码尝试记录。
```

具体规则：

- 用户贴代码且 AI / 后端守卫判断应进入 `review_code`，生成代码尝试记录。
- 用户直接粘贴代码，或先写“这是我的解答思路”再粘贴代码时，后端先截取明确代码候选，再交给 AI 判断是否进入 `review_code`。
- 用户贴代码但当前流程没有进入 `review_code`，不生成代码尝试记录。
- 当前进入 `review_code` 但本轮消息没有明确代码块或足够像代码的内容，不强行生成记录。
- 伪代码、复杂度表达、题意思路和普通对话不生成代码尝试记录。
- 生成代码快照时只保存截取出的代码块，不保存前置说明、尾部追问或其他聊天文本。

这个约束避免从所有聊天记录中做宽泛扫描，减少误提取。

### 6.3 展示方式

“代码尝试记录”点击后以居中悬浮框列表展示。

每条记录展示：

- 尝试序号，例如“第 1 次尝试”。
- 创建时间。
- 语言。
- 默认折叠的完整代码块。
- AI 质量判断状态。
- 感叹号图标，悬停展示 AI 简评。

### 6.4 状态语义

代码尝试记录有三种状态：

| 状态 | 图标 | 含义 |
| --- | --- | --- |
| 待评估 | 灰色 | 已提取代码，但 AI review 尚未完成或未形成明确判断。 |
| 建议修改 | 红灯 | AI 认为这版代码存在明显问题，不建议直接提交。 |
| 可尝试提交 | 绿灯 | AI 认为这版代码可以去 LeetCode 尝试提交。 |

红灯和绿灯只表示 AI 对代码质量的判断，不表示 LeetCode 判题结果。

### 6.5 AI 简评

每条代码尝试记录可以有一个感叹号图标。鼠标悬停展示 AI 对该代码版本的一句短评。

简评要求：

- 简短，优先一到两句话。
- 聚焦可行动问题或可提交依据。
- 不展示完整题解。
- 不包含大段用户代码。

示例：

```text
边界用例 [3,3], target = 6 可能失败，请检查 complement 命中后返回下标的逻辑。
```

```text
哈希表维护和复杂度判断基本正确，可以去 LeetCode 尝试提交。
```

## 7. LeetCode 已 AC

聊天输入区新增“LeetCode 已 AC”按钮。

用户点击后表示：

- 用户已经在 LeetCode 官网通过本题。
- 本题最终结果记为 AC。
- 系统可以进入 `summarize` 阶段。
- 系统触发或引导生成单题复盘。

MVP 阶段不要求用户填写运行时间和内存消耗。执行时间和内存对训练闭环价值较低，后续如果需要做性能对比或冲刺训练，再作为可选字段加入。

LeetCode 已 AC 是用户声明的最终事实，优先级高于 AI 对代码尝试记录的红绿灯判断。

## 8. 数据与后端影响

现有 `code_snapshot` 能力应保留，但前端入口从独立代码卡片迁移为聊天流自动生成。

建议新增或补充以下语义：

- `code_snapshot.source` 支持从聊天 review 产生，例如 `chat_review` 或复用 `before_review`。
- 代码尝试记录可以基于 `code_snapshot` 展示。
- AI review 完成后，`coach_turn` 或关联 payload 写入代码质量判断：
  - `quality_status`: `pending | needs_fix | ready_to_submit`
  - `quality_comment`: 简短 AI 简评
- LeetCode 已 AC 可以复用现有 `submission_feedback`，只提交 `result=ac`，不强制 runtime / memory。

当前后端要求提交反馈必须关联代码快照。新的交互下需要评估是否放宽 AC 场景：

- 如果最近有代码尝试记录，AC 关联最近一次代码快照。
- 如果没有代码尝试记录，允许用户标记 AC，但复盘中说明“本次 AC 未关联代码版本”。

这样可以避免用户已经在 LeetCode AC，却因为没有先在站内保存代码而无法结束训练。

## 9. 前端影响

需要调整的主要页面：

- `frontend/src/pages/WorkspacePage.tsx`：从三栏改为两栏，移除主界面的独立代码卡片。
- `frontend/src/pages/workspace/CoachPanel.tsx`：改为 ChatGPT 式聊天主界面，顶部保留轻量状态和代码尝试记录入口。
- `frontend/src/pages/workspace/CodePane.tsx`：不再作为工作台主卡片使用，可以删除、降级为内部组件，或后续复用为代码尝试记录悬浮框内的代码查看组件。
- `frontend/src/pages/workspace/SubmissionFeedbackModal.tsx`：MVP 可简化为 AC 动作和必要失败结果入口；AC 不要求 runtime / memory。

UI 重点：

- 聊天流是主体验，不再把事件时间线作为技术日志直接展示。
- 画像摘要默认不占据主视觉，可以折叠在上下文信息中。
- 代码尝试记录入口在聊天区顶部，列表通过居中悬浮框打开，代码默认折叠。

## 10. 测试策略

前端测试应覆盖：

- 工作台渲染为题面 + 教练两栏。
- 页面不再展示独立代码草稿卡片。
- 进入 `review_code` 后，聊天代码生成代码尝试记录入口数据。
- 非 `review_code` 阶段的代码样文本不生成代码尝试记录。
- 代码尝试记录展示待评估、建议修改、可尝试提交三种状态。
- 感叹号悬停可展示 AI 简评。
- 点击“LeetCode 已 AC”会记录 AC 并触发复盘流程。

后端测试应覆盖：

- AC 可以不带 runtime / memory。
- AC 在有最近代码快照时自动关联最近快照。
- 如果决定放宽 AC 无代码快照，需覆盖无代码快照也能记录 AC。
- AI 质量判断只作为代码尝试记录状态，不覆盖真实提交结果。

## 11. 文档影响

需要同步更新：

- `docs/prd/ai-coach-workbench-prd.md`：明确工作台采用题面 + Chat-first 教练布局；代码尝试记录来源于 `review_code` 阶段的代码提取；红绿灯是 AI 质量判断。
- `docs/architecture/foundation.md`：更新当前工作台前端描述，不再说左侧展示题目与代码草稿。
- `docs/project-todolist.md`：将后续工作台任务描述从“代码草稿卡片 + 提交回填”调整为“聊天式教练 + 代码尝试记录 + AC 动作”。

如果只先完成本文档，不修改代码和 PRD，则后续实现前必须先做上述文档同步，避免旧文档继续指向三栏工作台。

## 12. 验收标准

- 用户进入计划题工作台后，第一屏只有题面和教练聊天两个主要区域。
- 用户可以在聊天中描述思路、请求提示、贴代码 review。
- 只有进入 `review_code` 阶段的明确代码会生成代码尝试记录。
- 代码尝试记录能展示灰色、红灯、绿灯三种 AI 判断状态。
- 感叹号悬停能看到 AI 对该代码版本的短评。
- 用户点击“LeetCode 已 AC”后，本题进入 AC / 复盘流程。
- AC 不强制填写执行时间和内存。
- 红绿灯不会被表述为真实 LeetCode 判题结果。
