# PRD：面向 AI 教练决策的用户画像

## 1. 文档目的

本文档描述 AI 教练使用的用户画像产品需求。

它补充 `docs/prd/prd.md` 和 `docs/prd/ai-coach-workbench-prd.md` 中关于“用户学习画像”“画像驱动起手提问”和“复盘沉淀”的细节，重点回答：

- 用户画像在第一版产品中服务什么决策。
- 画像应该关注哪些训练指标。
- 画像如何从目标校准、训练事实和单题复盘中更新。
- LLM 在画像更新中负责什么，后端需要守住什么边界。
- AI 教练如何使用画像决定第一问、状态跳转、提示档位和 review 重点。

本文档是产品需求文档，不定义具体数据库表结构、API 路径、Prompt 模板或 LangGraph 实现。工程实现应以架构文档、设计规格和实施计划为准。

## 2. 产品定位

用户画像不是用户档案页，也不是单纯的数据统计面板，而是 **AI 教练做训练决策时使用的长期训练记忆**。

普通用户画像可能回答：

```text
这个用户是谁，有哪些标签。
```

本产品中的用户画像要回答：

```text
面对当前计划中的这道题，AI 教练应该怎么教这个用户。
```

因此，第一版画像的核心作用是帮助 AI 教练判断：

- 当前题应该从哪个训练阶段开始。
- 第一句话应该问什么。
- 用户是否可以跳过基础追问。
- 用户卡住时应该给什么档位的提示。
- 代码 review 应重点检查什么。
- 单题复盘后，下一次训练策略应该如何变化。

## 3. 第一版边界

### 3.1 第一版优先服务对象

第一版画像只优先服务做题工作台的 Chat-first AI 教练区。

它直接服务以下产品行为：

- 个性化第一问。
- 训练状态快进和回退。
- 提示档位建议。
- 代码 review 重点选择。
- LeetCode 提交反馈分析重点选择。
- 单题复盘后的画像更新和下一题建议。

### 3.2 第一版不优先服务对象

第一版不把画像做成完整学习仪表盘或复杂推荐系统。

以下能力可以预留，但不作为第一版验收重点：

- 完整能力雷达图。
- 多维趋势图。
- 全局题单推荐系统。
- 同类用户对比。
- 学习时长预测。
- 面试通过率预测。

### 3.3 明确不做

第一版不做以下事情：

- 不做通用用户标签系统。
- 不做完整能力考试评分。
- 不把完整聊天记录直接当画像。
- 不让 LLM 直接覆盖用户画像。
- 不要求画像每轮对话实时更新。
- 不把单次训练中的偶然失误立即扩大成长期结论。
- 不把用户隐私、完整代码和完整题解写入长期画像摘要。

## 4. 核心原则

### 4.1 决策优先

画像字段必须能影响 AI 教练行为。

如果一个字段不能帮助 AI 决定“问什么、跳到哪、提示多少、review 什么”，第一版不应优先维护。

### 4.2 事实和结论分离

系统应区分：

```text
训练事实：用户做了什么、提交了什么结果、用了什么提示档位。
画像结论：系统认为用户在哪些能力上稳定或薄弱。
教练策略：下一次训练应该如何调整。
```

事实是画像更新的依据，画像结论不能凭空生成。

### 4.3 增量更新

画像不应由 LLM 每次重新生成完整版本。

推荐流程是：

```text
训练事实
+ 上一次画像
+ 本题复盘
-> LLM 生成画像更新建议
-> 后端校验和合并
-> 生成新的画像版本
```

LLM 负责提出可解释的 `profile_patch`，后端负责守住合并规则和版本记录。

### 4.4 可解释和可追溯

画像中的关键结论必须能追溯到证据。

例如，系统不应只保存：

```text
边界条件薄弱。
```

而应保存：

```text
边界条件薄弱。最近 3 次哈希表训练中，2 次 WA 与重复元素或空结果边界有关。
```

### 4.5 近期信号优先，但不能遗忘长期趋势

AI 教练起手问题更依赖近期状态，长期画像用于防止被单次表现误导。

例如：

- 用户长期实现能力稳定，但最近一道题代码写错，不应立刻降级为“实现薄弱”。
- 用户长期在边界条件反复犯错，即使最近一题 AC，下一次仍应适度追问边界。

## 5. 画像核心结构

第一版画像建议分为四层。

### 5.1 用户当前训练水平

训练水平用于决定起手难度和默认训练密度。

| 水平 | 产品含义 | 典型教练行为 |
| --- | --- | --- |
| 入门 | 刚开始建立刷题流程，容易不知道从哪里开始 | 先确认题意和暴力解法，更早发现基础缺口 |
| 进阶 | 能理解题解，但独立推导和稳定实现不足 | 聚焦优化推导、不变量、边界和代码质量 |
| 面试冲刺 | 已有基础，需要提升表达、节奏和抗追问能力 | 更像面试官，追问复杂度、取舍和表达清晰度 |

训练水平不应只来自用户自评，也要结合最近训练事实动态调整。

### 5.2 能力维度

能力维度应直接对齐 AI 教练状态机。

第一版建议维护以下维度：

| 维度 | 关注点 | 影响的 AI 教练行为 |
| --- | --- | --- |
| 题意理解 | 是否能说清输入、输出、约束和目标 | 是否从 `understand_problem` 起手 |
| 暴力解法表达 | 是否能先给出直接可行方案 | 是否需要先要求用户讲暴力解法 |
| 优化推导 | 是否能从暴力方案推导到更优方案 | 是否进入 `optimize_solution` |
| 不变量 / 状态定义 | 是否能说清数据结构或状态维护什么 | 是否追问哈希表、双指针、DP 状态等含义 |
| 边界条件 | 是否主动覆盖空、重复、极值、无解等情况 | 是否优先要求列测试用例 |
| 代码实现 | 是否能把思路稳定写成代码 | 代码 review 是否聚焦实现细节 |
| 调试定位 | WA/TLE/RE 后是否能定位问题区域 | 提交反馈分析是否先让用户自查 |
| 复杂度表达 | 是否能准确说明时间和空间复杂度 | 复盘和面试追问是否强化复杂度 |
| 面试表达 | 是否能有条理地讲清思路和取舍 | 是否启用面试式追问 |

每个维度不应只是一个分数，还需要至少包含：

- 当前判断。
- 置信度。
- 最近证据摘要。
- 最近更新时间。

### 5.3 题型掌握度

题型掌握度用于决定同一道题的训练重点。

第一版建议覆盖：

- 数组。
- 哈希表。
- 双指针。
- 滑动窗口。
- 栈 / 队列。
- 二分。
- 树。
- 图。
- 动态规划。

题型画像不应只表达“会”或“不会”，而应描述更具体的训练信号。

示例：

```text
哈希表：能想到使用 map，但经常说不清 map 中维护什么，以及遍历到当前元素时要查什么。
```

```text
动态规划：能接受状态转移解释，但自己定义状态和初始化时不稳定。
```

### 5.4 教练策略建议

教练策略建议是决策型画像最重要的一层。

它不只是描述用户，而是直接告诉 AI 教练下一次应该如何工作。

第一版建议包含：

| 策略项 | 产品用途 |
| --- | --- |
| 推荐起手阶段 | 决定第一问从题意、暴力、优化、代码还是复盘开始 |
| 默认提示档位 | 决定默认使用追问档、方向档、关键档还是复盘档 |
| 应重点追问的问题 | 给 AI 第一问和后续追问提供方向 |
| 代码 review 重点 | 指导 AI 优先检查边界、循环条件、变量更新、返回值或复杂度 |
| 是否适合面试式追问 | 决定是否强调表达、时间节奏和面试官追问 |
| 是否需要优先检查边界用例 | 针对边界薄弱用户提高边界训练权重 |
| 是否应该避免重复基础问题 | 防止熟练用户被低价值问题打断 |

示例：

```text
下一次哈希表题不要直接要求代码。先追问用户“哈希表里维护什么”和“遍历到当前元素时要查什么”，再进入代码阶段。
```

## 6. 画像输入来源

画像应从结构化事实和复盘中更新，不应直接从完整聊天原文中粗暴总结。

第一版输入来源包括：

| 来源 | 典型信号 | 用途 |
| --- | --- | --- |
| 目标校准 | 用户目标、时间线、每周投入、默认语言、自评弱项 | 生成初始画像和训练水平 |
| 学习计划 | 阶段目标、重点标签、推荐理由、训练模式 | 提供当前训练上下文 |
| 训练状态事件 | 进入过哪些状态、是否快进、是否回退 | 判断能力覆盖和卡点 |
| 提示档位 | 主动请求提示、最高提示档位、升档原因 | 判断独立完成度和提示依赖 |
| 用户输入类型 | 思路、卡点、代码、提交结果、复盘请求 | 判断当前阶段和能力表现 |
| 代码 review 结果 | 错误类型、复杂度问题、边界问题、实现问题 | 更新实现、边界和调试维度 |
| LeetCode 回填 | AC、WA、TLE、RE、MLE、CE、失败用例 | 更新结果、错因和复盘重点 |
| 单题复盘 | 主要卡点、最高提示档位、画像信号、下一题建议 | 生成画像更新建议 |

## 7. 画像更新流程

### 7.1 初始画像

用户完成目标校准和学习计划确认后，系统可以生成初始画像。

初始画像主要来自：

- 用户自评弱项。
- 目标和时间线。
- 默认训练语言。
- 计划阶段和重点标签。

初始画像必须标记为低置信度，因为它主要来自用户自述和计划推断，还没有足够训练事实。

### 7.2 单题训练中

训练过程中可以记录事实，但不建议每轮对话都改长期画像。

原因：

- 单轮聊天信号噪声高。
- 用户可能只是临时表达不完整。
- 频繁更新容易让画像漂移。

训练中可以维护会话级临时判断，用于本题状态跳转；长期画像应在复盘后更新。

### 7.3 单题复盘后

一次训练结束并生成单题复盘后，系统生成画像更新建议。

推荐流程：

```text
本题训练事实
+ 本题复盘
+ 上一次长期画像
-> LLM 或规则化服务生成 profile_patch
-> 后端校验 profile_patch
-> 合并到长期画像
-> 记录画像版本和证据
```

`profile_patch` 应表达增量，而不是完整重写画像。
当前第一版先用后端规则化复盘事实生成安全 `profile_patch`，后续可以替换为 LLM 生成建议；无论来源如何，后端都负责守住合并规则和版本记录。

示例：

```text
维度：边界条件
变化：下调
置信度：中
证据：本题 WA 失败用例涉及重复元素；用户复盘时未主动提到重复元素处理。
策略建议：下一次哈希表题起手先要求列出 3 个边界用例。
```

### 7.4 合并规则

后端合并画像时应遵守：

- 没有证据的更新不合并。
- 低置信度更新不能大幅改变长期画像。
- 单题负向信号不能直接覆盖长期稳定正向信号。
- 最近多次同类证据可以提高置信度。
- 画像版本必须保留更新来源和摘要。
- 涉及敏感信息、完整代码、完整题解的内容不得进入长期画像摘要。

## 8. LLM 与后端职责边界

### 8.1 LLM 负责

LLM 可以负责：

- 从复盘和结构化事实中识别画像信号。
- 生成画像更新建议。
- 给出证据摘要。
- 生成下一次教练策略建议。
- 解释为什么某个信号影响画像。

### 8.2 后端负责

后端必须负责：

- 保存训练事实。
- 保存画像版本。
- 校验 LLM 输出结构。
- 校验更新是否有证据。
- 控制更新幅度。
- 过滤敏感信息。
- 决定是否合并 `profile_patch`。
- 为 AI 教练提供稳定、可控、可追溯的画像摘要。

### 8.3 不允许的模式

以下模式不应进入第一版：

```text
上一次画像 + 原始聊天全文 -> LLM 直接输出下一次完整画像 -> 覆盖保存
```

风险包括：

- 错误结论被连续放大。
- 模型把聊天噪声当长期事实。
- 画像缺少证据。
- 后续难以解释为什么 AI 教练这样提问。

## 9. 画像如何驱动 AI 教练

### 9.1 个性化第一问

进入计划题工作台时，AI 教练读取画像、计划目标和题目上下文，生成个性化第一问。

| 用户画像 | 第一问策略 |
| --- | --- |
| 入门，题意理解弱 | 先要求用户复述输入、输出和最直接做法 |
| 进阶，优化推导弱 | 直接要求从暴力方案说起，并追问可复用信息 |
| 哈希表不变量弱 | 先问哈希表维护什么、遍历时查什么 |
| 边界条件薄弱 | 先要求列出必须覆盖的边界用例 |
| 面试冲刺 | 要求用户按面试表达结构讲思路、复杂度和边界 |

### 9.2 状态快进

如果用户画像显示基础较强，且当前输入已经覆盖阶段验收点，系统应允许快进。

例如：

```text
用户已清楚说明题意、O(n) 思路、哈希表维护内容和复杂度。
AI 可以跳过题意理解和暴力解法阶段，直接进入代码或 review。
```

快进时必须给出简短原因。

### 9.3 状态回退

如果用户在后续阶段暴露前置能力缺口，系统应允许回退。

例如：

```text
用户已经写代码，但反复漏掉重复元素边界。
AI 可以从代码 review 回退到边界用例设计或不变量说明。
```

回退不是惩罚，而是更准确地定位训练问题。

### 9.4 提示档位

画像可以影响默认提示策略，但不能绕过提示档位边界。

要求：

- 独立性弱的用户可以更早建议升档。
- 熟练用户默认保持更克制的追问。
- 低提示档位下不能因为画像薄弱就直接给完整答案。
- 复盘必须记录最高提示档位，并说明它对独立完成度的影响。

### 9.5 代码 review

AI 代码 review 应结合历史弱点选择重点。

| 历史画像信号 | Review 重点 |
| --- | --- |
| 边界条件薄弱 | 空输入、重复元素、无解、极值 |
| 实现细节薄弱 | 循环条件、变量更新顺序、返回值 |
| 复杂度表达薄弱 | 是否存在隐藏嵌套循环，空间使用是否可解释 |
| 调试定位薄弱 | 先引导用户基于失败用例缩小问题范围 |

## 10. 对用户可见性

第一版画像主要给 AI 教练使用，不要求做完整画像页。

但在复盘中应让用户看到画像变化的可解释摘要。当前复盘页会读取已保存的 `session_summary`、`profile_delta` 和下一步建议，展示画像更新摘要和增量状态；学习仪表盘提供完成题数、常见卡点、平均/最高提示档位和最近画像摘要。更完整的能力趋势图和题型掌握度后续再扩展。

示例：

```text
本题对你的画像影响：
- 哈希表不变量表达有所加强：你能说清 map 中维护已访问数字。
- 边界条件仍需加强：WA 用例暴露了重复元素处理问题。
- 下一次同类题建议先列边界用例，再写代码。
```

用户不需要看到内部置信度计算细节，但应该能理解 AI 为什么下一次会这样训练他。

## 11. MVP 范围

### 11.1 第一版必须完成

- 支持从目标校准和学习计划生成初始画像摘要。
- 支持在进入计划题时为 AI 教练提供画像摘要。
- 支持画像影响个性化第一问。
- 支持画像影响状态快进、回退和提示档位建议。
- 支持单题复盘生成画像更新建议。
- 支持后端校验并合并画像更新建议。
- 支持画像版本和证据摘要追溯。

### 11.2 第一版可以简化

- 能力维度可以先使用粗粒度等级，不要求精细分数。
- 题型掌握度可以先覆盖学习计划中出现过的标签。
- 置信度可以先用高 / 中 / 低表达。
- 画像更新可以先只在单题复盘后触发。
- 用户可见内容可以先放在单题复盘和最小学习仪表盘中，不做完整画像管理页。

### 11.3 第一版不做

- 不做全局画像管理后台。
- 不做用户之间的画像对比。
- 不做长期趋势图。
- 不做自动重新生成整份学习计划。
- 不做基于画像的全自动题单推荐闭环。
- 不把完整聊天历史作为长期画像上下文保存。

## 12. 成功标准

### 12.1 体验成功标准

- 不同画像用户进入同一道题时，AI 第一问明显不同。
- 熟练用户不会反复被要求回答低价值基础问题。
- 边界薄弱用户会更早被要求列测试用例。
- 用户直接贴代码时，AI 能结合画像进入有重点的 code review。
- 用户完成复盘后，能看到本题对画像的具体影响。
- 下一次同类题训练能体现上一题复盘中的画像变化。

### 12.2 可量化指标

- AI 第一问画像匹配率。
- 熟练用户被重复问基础问题的比例。
- 用户首轮回复后的继续互动比例。
- 状态快进 / 回退原因可解释率。
- 单题复盘生成画像更新建议的比例。
- 画像更新建议被后端接受的比例。
- 同类题下一次训练中画像策略被引用的比例。

### 12.3 质量指标

- 用户画像引用准确率。
- 无证据画像更新比例。
- 画像更新漂移率。
- 低提示档位下完整答案泄露率。
- 复盘中的画像变化可解释性。

## 13. 与现有 PRD 的关系
