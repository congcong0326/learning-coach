# RAG 产品需求：教练知识库与计划增强

## 1. 文档目的

本文档定义 Agentic Coding Learning Coach 中 RAG 的产品定位、目标效果、使用场景、知识形态、提示档位边界和验收标准。

本文档不展开数据库表、embedding 模型、切块算法、LangGraph 节点实现或具体导入脚本。工程实现以架构文档、实施计划和实际代码为准；候选材料清单以 `docs/prd/rag-materials.md` 为准。

## 2. RAG 的产品定位

RAG 在本项目中不是通用资料搜索，也不是把完整题解塞进模型上下文。

RAG 的产品定位是：把本地整理的算法教程、题型路线、常见错误、提示策略和面试表达材料，转化为可过滤、可追踪、可约束泄露程度的“教练知识”，用于让 AI 教练更稳定地完成诊断、引导、review、复盘和计划设计。

它必须服务主产品目标：让用户更少依赖答案，更多形成可迁移的独立解题能力。

## 3. 为什么需要 RAG

当前非 RAG AI 教练已经能基于题面、用户输入、学习计划、训练事件和画像进行对话。但只依赖模型参数和当前上下文，会有几个产品问题：

- 教练风格不稳定：同一题型有时直接给题解，有时追问过多，有时忽略关键不变量。
- 题型知识不够一致：滑动窗口、双指针、动态规划、图搜索等题型缺少统一的识别信号、推导路径和常见错误库。
- 代码 review 容易泛泛而谈：模型可能指出“边界问题”，但不能稳定说明是哪类边界、为何破坏状态或不变量。
- 复盘训练价值不稳定：做完一题后，用户需要知道“这题训练了什么、下次如何识别、还应该练哪组题”，而不只是看到一段总结。
- 学习计划依据不够可解释：计划生成如果只靠模型泛化知识，容易像临时拼题单，缺少来自题型路线和材料体系的证据。

RAG 的价值是给 AI 教练提供外部、稳定、可审计的训练知识来源，同时继续让后端守卫控制提示档位和泄题边界。

## 4. 目标效果

### 4.1 P0：提升 AI 教练回答质量

第一阶段 RAG 优先服务做题工作台。用户应该感受到：

- AI 更像教练，而不是题解生成器。
- AI 对同一类题的追问、提示和复盘有稳定结构。
- AI 能根据题型知识卡片追问关键不变量、边界条件和复杂度来源。
- AI 代码 review 能结合常见 bug 卡片指出问题类型、影响范围和优先检查输入。
- AI 复盘能沉淀题型、识别信号、关键思路、常见误区和下一题训练建议。

### 4.2 P1：辅助学习计划设计

第二阶段 RAG 服务目标校准、学习计划生成和计划调整。用户应该感受到：

- 计划阶段不只是按难度排题，而是围绕题型路线、材料路线和用户弱项组织。
- 推荐理由能说明为什么当前阶段练这些题型、这些题之间是什么递进关系。
- 计划调整能结合近期复盘和画像弱项，补充对应题型材料、练习顺序和复盘重点。
- 冲刺面试时，计划能引用面试表达类卡片，安排“会做题”到“会讲题”的训练。

### 4.3 P2：支持可观测和评估

RAG 还要服务 Agent 工程质量：

- 每次检索必须可追踪，能看到 query 摘要、过滤条件、命中 chunk、被过滤原因和最终注入上下文。
- RAG Grounding Eval 应验证回复是否基于允许召回的材料。
- Hint Leakage Eval 应验证低提示档位不会因为检索命中完整题解而泄题。

## 5. 知识来源与知识形态

### 5.1 候选材料

候选材料来自 `docs/prd/rag-materials.md`，优先使用其中 P0 材料：

- 代码随想录。
- labuladong 的算法笔记。
- Hello 算法。
- LeetCode 101。
- NeetCode Roadmap / NeetCode 150。
- AlgoMonster 或 Grokking the Coding Interview。

后续再按需引入 P1 基础教材、竞赛专题和 P2 面试表达材料。

材料必须由用户本地整理或具备可使用授权。系统只负责解析、清洗、切块、抽取卡片和记录来源，不负责绕过版权、付费墙或平台限制。

### 5.2 不直接检索完整原文

第一版不把整篇教程、完整章节或完整题解作为默认 RAG 输入。优先从材料中抽取面向教练场景的派生卡片：

| 卡片类型 | 产品用途 |
| --- | --- |
| `concept_card` | 解释基础概念、术语、复杂度和数据结构特性。 |
| `pattern_card` | 描述题型模式、识别信号、适用条件和推导方向。 |
| `invariant_card` | 描述解法成立所依赖的不变量、状态定义或维护规则。 |
| `common_bug_card` | 描述常见实现错误、边界遗漏、复杂度误判和调试方向。 |
| `hint_card` | 提供分层提示，必须标注适用提示档位。 |
| `problem_coach_card` | 面向单题的教练视角，说明训练重点和追问方向，不等同于完整题解。 |
| `interview_expression_card` | 帮助用户组织面试表达、复杂度解释和复盘话术。 |
| `plan_path_card` | 描述题型路线、阶段目标、题单关系和先后依赖，用于计划设计。 |

### 5.3 必要元数据

每个知识卡片或 chunk 至少需要支持以下元数据：

| 字段 | 产品用途 |
| --- | --- |
| `source_name` / `source_url` / `source_locator` | 追踪知识来源和章节位置。 |
| `knowledge_type` | 区分概念、题型、bug、提示、表达、路线等知识。 |
| `problem_slug` / `problem_tags` | 支持按当前题目和题型召回。 |
| `difficulty` | 支持计划设计和提示难度控制。 |
| `phase` | 匹配理解题意、推导方案、写代码、review、提交反馈、复盘等阶段。 |
| `stuck_point` | 匹配用户当前卡点，例如不变量不清、边界遗漏、复杂度错误。 |
| `hint_level_min` / `hint_level_max` | 控制知识可在哪些提示档位出现。 |
| `has_full_solution` | 防止低提示档位召回完整解法或可提交代码。 |
| `language` | 支持中文教练回复和后续多语言训练材料。 |
| `quality_score` | 支持过滤低质量或抽取不稳定的卡片。 |

## 6. 使用场景

### 6.1 做题工作台：追问与分层提示

当用户描述题意困惑、思路卡住或请求提示时，RAG 应根据当前题目、计划阶段、训练模式、提示档位、用户画像和卡点召回 1 到 5 个知识片段。

不同提示档位的边界：

| 档位 | 允许召回 | 禁止召回 |
| --- | --- | --- |
| 追问档 | 概念澄清、题型识别信号、引导问题 | 题型答案、完整流程、伪代码、可提交代码 |
| 方向档 | 题型方向、可能数据结构、暴力到优化的思考方向 | 完整算法步骤、关键状态转移全量展开、完整代码 |
| 关键档 | 关键不变量、核心步骤、局部伪代码框架、常见 bug | 直接可提交的完整解法代码 |
| 复盘档 | 完整思路解释、复杂度分析、题型总结、面试表达 | 与用户训练无关的大段原文搬运 |

### 6.2 做题工作台：代码 Review

当用户粘贴代码或提交失败反馈时，RAG 应优先召回：

- 当前题型的 `common_bug_card`。
- 当前阶段相关的 `invariant_card`。
- 与错误类型相关的调试提示，例如 WA、TLE、RE、CE、MLE。
- 必要时召回语言相关实现注意点，但不替用户重写完整代码。

AI 可见回复应优先说明问题类型、可能位置、为什么会错、先检查哪个输入或边界。

### 6.3 单题复盘

AC 或等价终态后，RAG 可进入复盘档，召回更完整的题型总结、复杂度解释、常见误区和面试表达卡片。

复盘输出应帮助用户沉淀：

- 本题题型和识别信号。
- 解法成立的关键不变量或状态定义。
- 用户本次暴露出的主要卡点。
- 下次遇到同类题的检查清单。
- 下一题或下一组训练建议。

### 6.4 学习计划生成与调整

目标校准和计划调整阶段，RAG 不应召回单题完整题解，而应召回：

- `plan_path_card`：题型路线、阶段顺序、题单关系。
- `pattern_card`：题型之间的先修关系和迁移关系。
- `interview_expression_card`：面试冲刺阶段的表达训练建议。
- 用户画像和最近复盘摘要：用于决定补弱项，而不是机械照搬热门题单。

计划生成结果应说明每个阶段为什么这样安排、对应哪些题型能力、如何验证阶段完成。

## 7. 检索优先级与上下文预算

教练上下文优先级应保持与工作台 PRD 一致：

1. 当前题面和约束。
2. 当前学习计划、阶段目标和计划项推荐理由。
3. 用户长期画像。
4. 最近单题复盘摘要和画像增量。
5. 当前用户输入、最近关键事件、最新代码或提交反馈。
6. RAG 知识卡片。

RAG 片段不能挤掉当前题面、用户输入、代码证据和提交反馈。第一版每轮最多注入 3 到 5 个片段，并且只注入摘要化后的教练知识，不注入大段原文。

## 8. 安全边界与失败策略

- RAG 结果不能绕过 `coach_guard`，后端守卫仍负责最终提示档位和阶段迁移控制。
- 低提示档位必须过滤 `has_full_solution = true` 的内容。
- 检索命中质量低、来源不明确、档位不匹配或含完整答案风险时，应放弃注入并回退到非 RAG 教练流程。
- 模型不得在用户未进入复盘档时声称“根据资料完整解法是”。
- 检索上下文只保存来源、摘要和 chunk id，不应把完整用户输入、完整代码或敏感信息写入日志。
- 材料导入时必须记录来源和授权说明，避免把不应使用的付费或受限内容纳入默认知识库。

## 9. 产品范围

### 9.1 P0 必须完成

- 定义本地 source manifest 格式，能描述材料来源、语言、优先级和主要用途。
- 从第一批材料中抽取教练卡片，而不是默认检索完整原文。
- 支持 `knowledge_type`、`hint_level`、`has_full_solution`、题型标签和阶段过滤。
- 将检索结果接入做题工作台教练上下文。
- 在 Trace 中记录检索 query、过滤条件、命中片段、被过滤原因和最终注入片段。
- RAG Grounding Eval 从 `deferred` 升级为真实检查，并覆盖低提示档位不泄题。

### 9.2 P1 增强

- 将 `plan_path_card` 接入目标校准、计划生成和计划调整。
- 结合用户画像、近期复盘和题型路线生成更可解释的阶段计划。
- 支持按面试时间线和弱项自动选择材料路线。
- 将复盘沉淀的高质量摘要反向作为后续计划调整证据。

### 9.3 第一阶段不做

- 不做面向用户的通用资料搜索页。
- 不把 RAG 做成“问资料答资料”的聊天机器人。
- 不默认导入完整题解并在低提示档位使用。
- 不自动抓取 LeetCode、付费课程或未授权材料。
- 不把完整历史聊天、完整用户代码或敏感信息放入向量库。
- 不因为 RAG 命中结果就跳过用户画像、计划目标和训练状态机。

## 10. 验收标准

### 10.1 教练回答质量

- 追问档下，即使检索命中完整题解来源，AI 也不会输出题型答案、完整流程或伪代码。
- 方向档下，AI 能给出题型方向和思考路径，但不会直接给完整步骤。
- 关键档下，AI 能结合不变量或常见 bug 卡片给出可操作提示。
- 代码 review 中，AI 能把问题归因到明确 bug 类型或不变量破坏，而不是只给泛泛建议。
- 复盘中，AI 能输出题型识别信号、关键思路、复杂度、常见误区和下一题建议。

### 10.2 计划设计质量

- 学习计划阶段能说明对应题型能力和训练顺序。
- 推荐理由能结合用户目标、弱项、题型路线和材料路线。
- 计划调整能引用近期复盘中的证据，而不是只按未完成题目排序。
- 面试冲刺计划能加入表达训练和复盘表达要求。

### 10.3 可观测与评估

- Trace 页能看到 RAG 检索摘要、过滤条件、选中片段和最终注入状态。
- Eval runner 覆盖 RAG Grounding、Hint Leakage、Diagnosis 和 Code Review 的组合风险。
- 当检索结果被过滤或放弃注入时，系统记录稳定原因，例如 `hint_level_blocked`、`full_solution_blocked`、`low_quality`、`source_not_allowed`。

- `docs/prd/ai-coach-user-profile-prd.md`：定义用户画像，RAG 与画像共同影响教练第一问、提示策略和计划调整。
