# PRD：画像驱动的单题 AI 教练工作台

## 1. 文档目的

本文档描述做题工作台 AI 教练区的产品需求。

它补充 `docs/prd/prd.md` 中“做题工作台”和“AI 教练边界”的细节，重点回答：

- 用户进入一道计划题后，AI 教练区应该是什么体验。
- 聊天框如何和学习计划、题目、用户画像绑定。
- AI 如何根据用户水平、历史卡点和当前输入动态决定下一步。
- 如何避免教练区域退化成普通 ChatGPT 聊天框。
- 聊天过程如何沉淀为复盘、画像和后续 RAG 召回资产。

本文档是产品需求文档，不定义具体表结构、API 路径、Prompt 细节或 LangGraph 实现。工程实现应以架构文档、设计规格和实施计划为准。

## 2. 产品定位

AI 教练区不是通用聊天入口，而是“画像驱动的单题训练控制台”。

普通聊天产品的核心是：

```text
用户自由提问 -> AI 回答
```

本产品的核心是：

```text
用户进入当前计划中的一道题
-> 系统读取用户画像、计划目标、题目上下文和历史训练记录
-> AI 判断当前应从哪个训练阶段开始
-> AI 通过追问、提示、代码 review、提交反馈分析和复盘推进训练闭环
-> 系统沉淀本次训练对用户画像的影响
```

因此，AI 教练区的目标不是“让用户更快拿到答案”，而是“让用户以合适难度完成一次可诊断、可追踪、可复盘的训练”。

## 3. 核心原则

### 3.1 计划题上下文优先

AI 教练区必须从明确的训练上下文进入：

```text
用户 + 学习计划 + 题目
```

产品不提供一个脱离计划和题目的全局 AI 聊天入口。用户可以从题库自由选题进入工作台，但进入后仍应形成明确的训练会话上下文。

### 3.2 聊天框按学习计划复用

同一个用户在同一个学习计划下训练同一道题时，应复用同一个聊天框。

```text
同一个 user
同一个 study_plan
同一个 problem
=> 复用同一个 AI 教练聊天框
```

如果同一道题出现在新的学习计划中，应创建新的聊天框：

```text
同一个 user
新的 study_plan
同一个 problem
=> 新 AI 教练聊天框
```

原因是同一道题在不同计划中的训练目标可能不同。第一次可能是入门掌握，第二次可能是面试表达或边界条件专项复训，聊天历史不应混在一起。

### 3.3 计划版本不改变聊天框身份

学习计划可以调整并产生新的版本。计划版本用于追溯“这次训练来自哪一版计划”，但不应参与聊天框唯一身份。

例如：

```text
计划 A v1 包含 Two Sum，用户开始训练并产生聊天框。
计划 A 后续调整为 v2，Two Sum 仍然保留。
用户再次进入 Two Sum 时，仍应复用原聊天框。
```

也就是说，学习计划版本变化不能导致同一计划内的同一道题自动新建聊天框。

### 3.4 状态机是主干，聊天只是交互形式

AI 教练区看起来像聊天，但产品行为应由训练状态驱动。

典型训练阶段包括：

```text
理解题意
提出暴力解法
推导优化方案
说明关键不变量或状态定义
编写代码
代码 review
引导 LeetCode 提交
分析提交反馈
单题复盘
```

这些阶段不是固定线性流程。系统应允许根据用户画像和用户输入跳过已经满足条件的步骤。

### 3.5 LLM 负责判断，后端负责守卫

LLM 可以根据上下文判断用户当前水平、卡点和下一步动作，但系统状态不能完全交给 LLM 自由决定。

产品语义上应区分：

```text
LLM：提出诊断和下一步建议。
后端：校验跳转是否合法，记录状态变化，控制提示泄露边界。
```

这样既保留 AI 的灵活性，也避免模型错误跳转、过度提示或直接泄露完整答案。

## 4. 目标用户体验

### 4.1 进入工作台

用户从学习计划点击一道题进入工作台。

页面上方自然展开题面，下方展示 ChatGPT 式 AI 教练区。第一版不再在主界面放独立代码卡片；用户把思路、卡点和代码直接发给教练，发送后用户消息应立即进入聊天流，教练运行中用临时教练气泡展示当前状态或流式回复。系统只在进入 `review_code` 流程时自动提取代码并沉淀为代码尝试记录。AI 教练区不是空白聊天框，而是直接展示当前训练上下文：

```text
当前计划：春招算法冲刺
当前阶段：哈希表与数组
当前题目：Two Sum
训练目标：能独立从暴力解法推导到 O(n) 哈希表方案
训练模式：独立训练
提示档位：追问档
```

AI 的第一句话应根据用户画像生成，而不是固定模板。

### 4.2 初学用户的起手体验

如果用户画像显示该用户刚开始刷题，或者在题意理解、暴力解法表达上经常卡住，AI 起手应更基础：

```text
先不用写代码。你先用自己的话说一下：
这题的输入是什么、输出是什么，最直接的双重循环做法是什么？
```

产品目标是帮助用户建立基本解题流程，而不是立即进入优化。

### 4.3 熟练用户的起手体验

如果用户画像显示该用户基础较强，AI 不应反复问低价值问题。

起手可以直接要求用户说明关键思路：

```text
这题你可以直接给出 O(n) 思路：
哈希表里维护什么、遍历到当前元素时要查什么、如何处理重复元素。
```

产品目标是尊重用户水平，提高训练密度。

### 4.4 有明确历史弱点用户的起手体验

如果用户历史上在某类题里经常漏边界，AI 起手应围绕该弱点设计：

```text
你之前在哈希题里主要容易漏重复元素和空结果边界。
这题先不用写完整代码，先列出你认为必须覆盖的 3 个边界用例。
```

产品目标是让 AI 像了解用户的教练，而不是每题都从零开始。

### 4.5 用户直接给出清晰思路

如果用户第一条消息已经包含清楚的题意理解、最优思路、复杂度和边界，系统应允许跳过前置阶段。

预期体验：

```text
AI 判断用户已满足“理解题意”和“推导方案”的条件。
聊天框直接进入“编写代码”或“代码 review”阶段。
```

AI 回复不应机械地继续问：

```text
你能先复述一下题意吗？
```

### 4.6 用户直接粘贴代码

如果用户一进入就粘贴代码，系统应识别为代码 review 场景。

预期体验：

```text
AI 直接进入代码 review。
AI 优先检查当前代码的主要问题类型、可能出错区域和建议用户验证的输入。
```

如果代码已经接近可提交状态，AI 应推动用户去 LeetCode 提交，而不是继续泛泛讲思路。进入 `review_code` 后提取出的代码应出现在“代码尝试记录”中，记录包含 AI 对代码质量的红灯/绿灯判断和一条简短简评；红绿灯只表示 AI 对代码质量的判断，不等同 LeetCode 官方结果。

### 4.7 用户已经有 LeetCode 结果

如果用户直接提供“代码 + LeetCode 结果”，系统应快进到提交反馈分析。

示例：

```text
用户：这版代码 WA，失败用例是 [3,3], target = 6。
AI：系统进入提交反馈分析阶段，结合代码版本和失败用例定位问题。
```

如果用户提供 AC 结果，系统应进入复盘阶段，而不是继续要求用户解释基础思路。

## 5. 用户主流程

### 5.1 标准训练流程

```text
用户从学习计划选择题目
-> 创建或恢复该计划题的 AI 教练聊天框
-> 系统读取用户画像、计划目标、题目信息和历史会话
-> AI 生成个性化第一问
-> 用户描述思路、卡点或代码
-> 用户消息立即显示在聊天流中
-> 前端通过一行轻量状态展示后端当前步骤，例如准备上下文、调用大模型、校验阶段或保存回复
-> 教练回复以临时教练气泡展示，正式 assistant event 返回后再由会话历史接管
-> AI 诊断当前阶段和卡点
-> 系统决定是否跳转阶段
-> AI 追问、提示、review 或建议提交
-> 用户点击“LeetCode 已 AC”或在聊天中描述未通过结果
-> AI 分析提交反馈
-> 生成单题复盘
-> 更新用户画像和下一步建议
```

### 5.2 快进流程

当用户输入已经满足后续阶段条件时，系统应允许快进。

常见快进场景：

| 用户输入 | 系统应进入 |
| --- | --- |
| 清楚描述题意、暴力解法、优化思路和复杂度 | 编写代码或代码 review |
| 直接粘贴代码 | 代码 review |
| 粘贴代码并说明 WA/TLE/RE | 提交反馈分析 |
| 粘贴代码并说明 AC | 单题复盘 |
| 明确请求复盘 | 单题复盘，但需要检查是否已有足够训练证据 |

快进时，AI 需要简短说明原因：

```text
你的思路已经覆盖题意、哈希表维护内容和复杂度，我直接进入代码阶段。
```

### 5.3 回退流程

当用户暴露出前置能力缺口时，系统也应允许回退。

示例：

```text
用户在写代码阶段反复出现边界错误。
AI 可以从代码 review 回退到“边界用例设计”或“关键不变量说明”。
```

回退不是惩罚，而是更准确地定位训练问题。

## 6. AI 教练状态

### 6.1 状态列表

第一版建议使用以下产品状态：

| 状态 | 产品含义 | 典型 AI 行为 |
| --- | --- | --- |
| `understand_problem` | 理解题意 | 要求用户复述输入、输出和约束 |
| `propose_bruteforce` | 提出暴力解法 | 引导用户先写出最直接方案 |
| `optimize_solution` | 推导优化 | 引导用户发现可复用信息、数据结构或剪枝 |
| `define_invariant` | 明确不变量 | 追问哈希表、指针、DP 状态等维护含义 |
| `write_code` | 编写代码 | 要求用户提交代码或关键片段 |
| `review_code` | 代码 review | 定位逻辑区域、边界、复杂度和实现错误 |
| `submit_to_leetcode` | 引导提交 | 建议用户到 LeetCode 提交并回填结果 |
| `analyze_feedback` | 分析反馈 | 基于 AC/WA/TLE/RE 解释问题原因 |
| `summarize` | 单题复盘 | 生成复盘、画像更新和下一题建议 |

### 6.2 状态跳转原则

状态跳转应满足以下原则：

- 不要求所有用户都从 `understand_problem` 开始。
- 不要求所有状态都必须经历。
- 高水平用户可以跳过基础阶段。
- 用户输入代码时可以直接进入 `review_code`。
- 用户回填提交结果时可以直接进入 `analyze_feedback`。
- 用户 AC 后可以进入 `summarize`。
- 如果用户在后续阶段暴露基础缺口，可以回退到更早状态。

### 6.3 跳转判定依据

系统判断阶段跳转时，应综合以下信息：

- 用户当前画像。
- 当前学习计划目标。
- 当前题目的难度、标签和推荐理由。
- 用户本轮输入的意图。
- 用户是否提供代码。
- 用户是否提供 LeetCode 结果。
- 用户回答是否覆盖当前阶段验收点。
- 当前提示档位和训练模式。

## 7. 个性化需求

### 7.1 用户画像输入

AI 教练起手和后续追问应参考用户画像。

用户画像本身的产品定位、指标结构、更新机制和 LLM / 后端职责边界见 `docs/prd/ai-coach-user-profile-prd.md`。本文档只描述工作台如何消费画像。

第一版画像至少需要支持以下维度：

- 用户整体水平：入门、进阶、面试冲刺。
- 常见卡点：题意理解、题型识别、优化推导、不变量、边界条件、实现细节、复杂度表达。
- 题型掌握度：数组、哈希表、双指针、滑动窗口、栈、队列、二分、树、图、动态规划等。
- 历史最高提示档位。
- 独立完成比例。
- 最近训练结果。

### 7.2 个性化第一问

AI 的第一问必须根据用户画像和题目上下文生成。

第一问应避免两个极端：

- 对入门用户过早要求最优解。
- 对熟练用户重复问低价值基础问题。

### 7.3 个性化提示策略

同一道题对不同用户可以采用不同提示策略。

示例：

| 用户画像 | 提示策略 |
| --- | --- |
| 入门用户 | 更早确认题意和暴力解法，必要时更快提升提示档位 |
| 熟练用户 | 多追问不变量、复杂度和边界，不轻易给方向提示 |
| 面试冲刺用户 | 强调表达、时间节奏和面试官追问 |
| 边界薄弱用户 | 优先要求列测试用例和解释边界处理 |
| 实现薄弱用户 | 重点 review 变量更新顺序、循环条件和返回值 |

## 8. 用户输入与业务动作

AI 教练区应保留自然语言输入，但不应只依赖一个普通文本框。

用户主路径应是直接输入自然语言，系统负责识别意图，不要求用户先选择“描述思路”“我卡住了”“代码 Review”等消息分类。此类意图由模型结合文本和上下文判断，再由后端守卫控制状态跳转。

明确入口只保留给流程性或结构化动作，降低用户表达成本，也方便后端记录关键事实：

- 请求提示。
- 代码尝试记录：只读抽屉，来源于 `review_code` 流程中自动提取的代码。
- LeetCode 已 AC：表示用户已经在 LeetCode 官方提交通过，并触发复盘流程。

第一版不再保留泛化的“提交回填”弹窗作为主路径。WA、TLE、RE、CE 等未通过信息可以先由用户在聊天中描述，AI 根据当前代码尝试和失败信息进入分析；后续如需要更强结构化，再补充专门的失败反馈入口。

## 9. 提示档位要求

提示档位是产品状态，不只是前端标签。

第一版沿用四个用户可见档位：

| 档位 | 产品含义 |
| --- | --- |
| 追问档 | 只提问和澄清，不提示题型或数据结构。 |
| 方向档 | 提醒题型方向或可能的数据结构，不给完整流程。 |
| 关键档 | 提醒核心不变量、关键步骤或伪代码框架。 |
| 复盘档 | 可以解释完整思路，但仍不默认贴完整提交代码。 |

要求：

- AI 回复必须受当前提示档位约束。
- 用户可以主动请求更高提示档位。
- 系统可以建议提升提示档位，但应让用户感知原因。
- 会话必须记录最高提示档位。
- 复盘必须展示最高提示档位，并解释它对独立完成度的影响。

## 10. LeetCode 提交反馈

第一版以 LeetCode 官网提交结果为准，不在产品内自建判题。

AC 结果不应作为普通聊天文本散落在记录中。第一版通过“LeetCode 已 AC”按钮记录官方 AC，并允许在没有运行时间、内存或本地代码快照的情况下进入复盘；执行时间和内存消耗对训练闭环不是必填项。

未通过结果可以先通过聊天描述，AI 结合最近一次代码尝试、失败用例和错误信息进行分析。后续如果增加结构化失败反馈入口，应优先收集：

- 提交结果：WA、TLE、RE、MLE、CE、Unknown。
- 失败用例。
- 错误信息。
- 对应代码尝试记录。
- 用户自己的判断，可选。

AI 应根据提交反馈进入不同动作：

| 提交结果 | AI 行为 |
| --- | --- |
| AC | 引导复盘，确认复杂度、核心思路和可迁移经验 |
| WA | 定位错误类型、逻辑区域和优先检查用例 |
| TLE | 分析复杂度瓶颈和可优化方向 |
| RE | 分析越界、空值、递归深度等运行错误 |
| CE | 分析语法、类型或语言细节问题 |

## 11. 复盘沉淀

一次训练结束后，系统必须生成单题复盘。

复盘至少包含：

- 本题最终结果。
- 当前训练模式。
- 主要卡点。
- 使用过的最高提示档位。
- 是否经历快进或回退。
- 代码错误类型。
- 时间复杂度和空间复杂度掌握情况。
- 本题核心思路。
- 用户本题暴露出的画像信号。
- 对用户画像的更新建议。
- 下一题或下一组训练建议。

复盘目标不是简单总结聊天，而是把一次聊天变成训练资产。

## 12. RAG 与历史召回的产品要求

后续 AI 可以召回用户历史，但不应默认把完整聊天原文全部放入上下文。

推荐的召回优先级：

1. 用户长期画像。
2. 最近单题复盘摘要。
3. 画像增量和证据。
4. 当前计划目标和阶段目标。
5. 必要时召回关键历史事件。

原因：

- 完整聊天噪声高，容易干扰模型判断。
- 聊天里可能包含大段代码、错误思路或敏感内容。
- 复盘和画像更适合表达“用户真正需要补什么”。

产品上应让 AI 表现得“记得用户的训练历史”，但不是机械复读历史聊天。

## 13. 页面体验要求

### 13.1 工作台布局

做题工作台应至少包含：

- 上方自然展开的题面。
- 当前计划和阶段信息。
- 当前训练模式。
- 下方 Chat-first AI 教练区。
- 当前 AI 教练状态。
- 当前提示档位。
- LeetCode 原题入口。
- 代码尝试记录入口。
- LeetCode 已 AC 入口。

主界面不再包含独立代码卡片。代码沉淀来自聊天中的 `review_code` 流程，而不是用户在工作台中维护一份单独代码草稿。

### 13.2 AI 教练区

AI 教练区应展示：

- 对话时间线。
- 业务事件，例如代码尝试已记录、LeetCode AC 已记录、阶段已切换。
- 当前状态，例如“代码 review 中”“等待 LeetCode 结果”“复盘已生成”。
- 快进或回退原因的简短说明。
- 可操作按钮，例如请求提示、查看代码尝试记录、LeetCode 已 AC。

### 13.3 不应出现的体验

以下体验应避免：

- AI 第一问永远固定。
- 熟练用户仍被要求回答明显基础问题。
- 用户贴代码后，AI 仍按“先复述题意”流程走。
- 用户已经 AC，AI 仍继续提示解法。
- AI 在低提示档位直接给完整答案。
- LeetCode 结果只作为普通聊天文本散落在记录中。
- 聊天结束后没有复盘和画像沉淀。

## 14. MVP 范围

### 14.1 第一版必须完成

- 从学习计划题目进入工作台。
- 同一用户、同一学习计划、同一题目复用同一个聊天框。
- 学习计划版本变化不导致新建聊天框。
- AI 起手问题根据用户画像、计划目标和题目上下文生成。
- 支持基础训练状态：理解题意、推导方案、写代码、代码 review、提交反馈、复盘。
- 支持用户直接输入思路、卡点、代码或 LeetCode 结果后快进到合适状态。
- 支持提示档位约束。
- 支持 LeetCode 已 AC 结构化动作；非 AC 结果第一版可通过聊天描述并由 AI 分析。
- 支持单题复盘。
- 训练结果可以作为后续用户画像更新的输入。

### 14.2 第一版可以简化

- 用户画像可以先使用目标校准、自评弱项、计划标签和历史复盘摘要，不要求复杂模型。
- 状态机可以先使用有限状态和后端守卫，不必一开始接完整 LangGraph。
- RAG 可以先不接真实向量检索，但要预留“复盘和画像优先于原始聊天”的产品原则。
- 面试模拟模式可以先复用基础状态，只增加时间节奏和表达追问。

### 14.3 第一版不做

- 不做脱离题目和计划的全局 AI 聊天。
- 不自动提交 LeetCode。
- 不抓取 LeetCode 隐藏用例。
- 不在低提示档位提供完整可提交题解。
- 不把完整历史聊天无筛选地放入模型上下文。
- 不要求所有训练状态都必须在第一版实现成复杂图编排。

## 15. 成功标准

### 15.1 体验成功标准

- 用户能感受到 AI 知道自己当前在练哪道题、为什么练这道题。
- 不同水平用户进入同一道题时，AI 起手问题明显不同。
- 用户直接给出高质量思路时，AI 能跳过基础追问。
- 用户直接粘贴代码时，AI 能直接进入代码 review。
- 用户回填 LeetCode 结果后，AI 能围绕结果继续分析或复盘。
- 完成一题后，用户能看到明确复盘，而不是只留下聊天记录。

### 15.2 可量化指标

- 从计划题进入工作台的比例。
- 工作台首轮 AI 回复后用户继续互动比例。
- 用户主动请求提示的平均档位。
- 训练状态快进比例。
- 代码 review 后代码尝试记录生成比例。
- 代码 review 后 LeetCode 已 AC 点击比例。
- 单题复盘生成比例。
- 单题复盘后继续下一题比例。
- 同一计划题再次打开时聊天框恢复成功率。

### 15.3 质量指标

- 低提示档位下完整答案泄露率。
- AI 错误状态跳转率。
- 用户画像引用准确率。
- 提交反馈归因有效率。
- 复盘摘要可解释性。

## 16. 与现有 PRD 的关系

`docs/prd/prd.md` 是产品总 PRD，定义第一版产品主线和边界。

本文档是做题工作台和 AI 教练区的专题 PRD，细化总 PRD 中以下能力：

- 从学习计划进入做题工作台。
- AI 教练对话区。
- 分层提示和代码 review。
- LeetCode 提交结果回填。
- 单题复盘和用户画像更新。

如本文档和总 PRD 发生冲突，应优先保持总 PRD 的产品边界，再更新本文档的细节。
